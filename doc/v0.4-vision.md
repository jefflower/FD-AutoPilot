# Simsonn AutoPilot v0.4 — 版本目标与迭代愿景

## 系统定位变更

**FD-AutoPilot → Simsonn AutoPilot**

从"智能工单处理系统"升级为**企业 AI 自动化平台**。工单处理（Ticket）是第一个业务模块，后续将接入采购、销售、财务等独立业务模块。每个业务模块共享平台级基础设施（认证、任务调度、AI Agent、工作流引擎），但拥有独立的业务逻辑和数据模型。

## v0.4 核心目标

### 1. 7 模块后端架构

将后端从 5 模块（common/auth/task/ticket/app）扩展为 7 模块，新增 **ai** 和 **workflow** 两个平台级模块：

```
fd-server/
├── fd-server-common/       公共基础（DTO、工具类、异常处理）
├── fd-server-auth/         认证授权（JWT、RBAC、用户生命周期、组织同步）
├── fd-server-task/         任务调度（多客户端分发、定时任务、超时回收）
├── fd-server-ai/           AI Agent 管理（定义、执行日志、能力绑定、SPI 扩展）
├── fd-server-workflow/     工作流引擎（Flowable BPMN 2.0、JavaDelegate、双轨模式）
├── fd-server-ticket/       工单业务（Freshdesk 集成、MQ 分发、知识库）
└── fd-server-app/          启动入口 + 资源 + 静态前端
```

**模块依赖链**：`common ← auth ← task ← ai ← workflow ← ticket ← app`

### 2. AI Agent 管理模块 (fd-server-ai)

将 AI 能力从硬编码升级为可管理的 Agent 体系：

- **Agent 定义管理** — 每个 Agent 有 code、name、providerType、executionEnv、capability 等属性，支持 CRUD + 启用/禁用
- **4 种 Provider 类型** — LOCAL_CLI（如 Gemini CLI）、HTTP_API（OpenAI/Claude）、SHADOW_WINDOW（NotebookLM）、LOCAL_FUNCTION（本地函数）
- **3 种执行环境** — CLIENT_ONLY（仅桌面端）、SERVER_ONLY（仅服务端）、BOTH（双端可用）
- **能力绑定** — capability → agentCode 映射，支持动态切换同类 Agent（如翻译能力从 Gemini 切换到 OpenAI）
- **SPI 扩展** — AgentProvider 接口，服务端 Provider 可插拔（内置 HttpApiAgentProvider）
- **执行日志** — 记录每次 Agent 调用的输入/输出/耗时/Token 用量，支持统计仪表盘
- **4 个内置 Agent** — gemini-translate、notebooklm-reply、tracking-query、antigravity-translate

### 3. 工作流引擎模块 (fd-server-workflow)

引入 Flowable BPMN 2.0 实现可视化、可编排的业务流程：

- **Flowable 集成** — 嵌入式引擎，仅启用 Process 引擎（禁用 CMMN/DMN/Form/Content/IDM）
- **3 种 JavaDelegate 节点类型**：
  - `AgentTaskDelegate` — AI Agent 执行节点，创建 TaskInstance → SSE 通知客户端 → 客户端执行 → REST 上报 → WorkflowTaskBridge 唤醒流程
  - `HumanTaskDelegate` — 人工任务节点（如审核），等待人工操作后继续
  - `BusinessCallbackDelegate` — 业务回调节点，通过 WorkflowCallbackRegistry 解耦，业务模块注册回调
- **双轨模式** — `fd.workflow.enabled` 配置开关：
  - `false`（默认）：使用 LegacyTicketOrchestrator，现有 MQ 驱动逻辑不变
  - `true`：使用 FlowableTicketOrchestrator，由 BPMN 流程定义驱动
- **异步唤醒链** — BPMN ServiceTask → AgentTaskDelegate → 创建 TaskInstance → SSE 推送 → 客户端 claim → 本地执行 → REST complete → WorkflowTaskBridge signal ReceiveTask → 流程继续
- **内置流程** — ticket-standard-flow.bpmn20.xml（工单标准处理流程）

### 4. 前端 Agent 运行时

统一的客户端 Agent 执行框架：

- **AgentRegistry** — 单例注册中心，从后端加载 Agent 定义，注册 Executor，按 code 或 capability 解析
- **4 种 Executor** — CliExecutor（CLI 工具调用）、HttpApiExecutor（HTTP API 调用）、ShadowExecutor（Shadow Window 操作）、FunctionExecutor（本地函数）
- **useAgent Hook** — 统一的 Agent 执行接口（execute/executeStream），自动上报执行结果到后端
- **AgentContext** — App 初始化时注册 Executor + 加载定义

### 5. SSE 实时推送

替代轮询的实时事件通知机制：

- **SseConnectionManager** — 管理客户端 SSE 长连接
- **EventStreamController** — SSE 端点（`/api/v1/events/stream`）
- **事件类型** — 任务分配通知、工单状态变更、Agent 执行完成等
- REST 轮询作为 SSE 不可用时的降级方案

### 6. 工作流管理 UI

前端工作流可视化管理：

- **BpmnEditor** — BPMN 2.0 流程图编辑器（基于 bpmn.io）
- **WorkflowListTab** — 流程定义列表管理
- **WorkflowGuideTab** — 工作流使用引导

### 7. 组织同步管理

企业组织架构同步能力：

- **OrgSyncTab** — 管理界面
- 支持企业微信/钉钉组织架构同步（预留接口）

## 架构设计原则

### 模块化隔离
- 严格的单向依赖：下游模块不得依赖上游（如 ai 不得 import workflow/ticket）
- 模块间通过注入 Service 直接调用，不做过度抽象
- 业务回调通过 Registry 模式解耦（如 WorkflowCallbackRegistry）

### 本地 Agent 保留
- Gemini CLI 翻译和 NotebookLM 回复**必须保留客户端执行**（无公开 API）
- 通过 executionEnv 标记区分执行位置
- 本地执行 → SSE/REST 上报结果 → 服务端更新状态

### 双轨渐进迁移
- 新旧工作流并存，通过配置开关切换
- 默认使用旧逻辑（MQ 驱动），验证稳定后切换到 Flowable
- 两种模式对外行为一致，仅内部编排机制不同

### 平台化扩展
- ai 和 workflow 是平台级模块，不限于工单业务
- 未来新业务模块（采购、销售、财务）可直接复用
- Agent 能力绑定机制支持同一能力在不同业务场景下使用不同 Agent

## Agent 标准化设计

本章定义 Simsonn AutoPilot 的 Agent 标准化设计规范。结合业界先进经验（Anthropic 可组合模式、Microsoft Azure Agent 编排模式、AAIF 开放标准、MCP 协议），建立统一的 Agent 定义、执行、编排和可观测性标准，确保后续所有新 Agent 均可遵循同一规范快速接入。

### 设计理念

> **"Start simple, scale incrementally"** — Anthropic 建议从简单的可组合模式开始，仅在明确改进结果时才增加复杂性。

我们的 Agent 标准化遵循以下原则：

1. **配置驱动而非代码驱动** — Agent 定义存储在数据库中，新增 Agent 无需重新编译部署
2. **能力与实现解耦** — 业务层只需声明需要的能力（capability），具体由哪个 Agent 执行由绑定配置决定
3. **统一执行模型** — 无论 Agent 在客户端还是服务端执行，对外暴露相同的接口和日志格式
4. **渐进式复杂度** — 单 Agent 能解决的问题不引入多 Agent 编排（参考 Azure 架构指南的复杂度分级）

### Agent 定义标准 (AgentDefinition)

每个 Agent 必须包含以下标准字段：

```
┌─────────────────────────────────────────────────────────┐
│                    AgentDefinition                       │
├──────────────────┬──────────────────────────────────────┤
│ code             │ 全局唯一标识（如 gemini-translate）     │
│ name             │ 人类可读名称                           │
│ description      │ 功能描述                              │
│ providerType     │ 执行方式（见下方 Provider 类型表）       │
│ executionEnv     │ 执行环境（见下方执行环境表）             │
│ capability       │ 能力标签（如 translation, reply）       │
│ providerConfig   │ Provider 专属配置（JSON 格式）          │
│ enabled          │ 是否启用                              │
│ builtIn          │ 是否内置（内置不可删除）                 │
│ sortOrder        │ 同能力 Agent 的优先级排序               │
└──────────────────┴──────────────────────────────────────┘
```

#### Provider 类型

参考 Anthropic 的"工具工程规范"和业界多模态 Agent 实践，定义 4 种 Provider 类型：

| Provider 类型 | 说明 | 适用场景 | 执行位置 |
|--------------|------|---------|---------|
| `LOCAL_CLI` | 调用本地 CLI 工具 | Gemini CLI 翻译 | 仅客户端（Tauri） |
| `HTTP_API` | 调用 OpenAI/Claude 兼容 HTTP API | 通用 LLM 调用、API 代理 | 服务端 或 双端 |
| `SHADOW_WINDOW` | 操作隐藏浏览器窗口 | NotebookLM 回复、17track 物流 | 仅客户端（Tauri） |
| `LOCAL_FUNCTION` | 调用预注册的本地 JS 函数 | 数据转换、格式处理 | 任意环境 |

#### 执行环境

| 执行环境 | 说明 | 典型场景 |
|---------|------|---------|
| `CLIENT_ONLY` | 仅客户端执行，服务端不可调度 | 无公开 API 的工具（Gemini CLI、NotebookLM） |
| `SERVER_ONLY` | 仅服务端执行，API Key 不暴露 | 付费 LLM API（OpenAI、Claude） |
| `BOTH` | 双端均可执行，按场景选择 | 通用 HTTP API Agent |

#### providerConfig 配置规范

每种 Provider 类型的 `providerConfig` 必须遵循以下 JSON Schema：

**LOCAL_CLI:**
```json
{
  "invokeCommand": "translate_ticket_direct_cmd",
  "timeout": 30000
}
```

**HTTP_API:**
```json
{
  "baseUrl": "https://api.openai.com/v1",
  "model": "gpt-4",
  "apiKey": "${API_KEY}",
  "maxTokens": 4096,
  "systemPrompt": "You are a translator..."
}
```

**SHADOW_WINDOW:**
```json
{
  "windowLabel": "notebook_shadow",
  "url": "https://notebooklm.google.com",
  "timeout": 120000
}
```

**LOCAL_FUNCTION:**
```json
{
  "functionName": "formatTicketData"
}
```

### 能力绑定标准 (Capability Binding)

能力绑定是将业务需求（capability）映射到具体 Agent（agentCode）的机制，实现**需求与实现解耦**。

```
业务代码 ──(capability: "translation")──→ AgentBindingService
                                            │
                                  ┌─────────┴──────────┐
                                  │ 查询绑定表           │
                                  │ capability → agentCode│
                                  └─────────┬──────────┘
                                            │
                            ┌───────────────┼───────────────┐
                            │               │               │
                   gemini-translate  antigravity-translate  openai-translate
                   (LOCAL_CLI)       (HTTP_API)             (HTTP_API)
```

**规则**：
- 一个 capability 同时只绑定一个 agentCode
- 未配置绑定时，按 sortOrder 选择该 capability 下的第一个 enabled Agent
- 管理员可通过 UI 实时切换绑定，无需重启服务
- 支持的 capability 标签需在 Agent 定义时声明，建议使用小写英文（如 `translation`, `reply`, `tracking`, `audit`）

### Agent 执行生命周期

参考 Anthropic 的"感知-决策-执行"闭环和 Azure 的可靠性设计，定义标准执行生命周期：

```
                    ┌──────────┐
                    │  IDLE    │
                    └────┬─────┘
                         │ execute()
                         ▼
                    ┌──────────┐
        ┌──────────│ RUNNING  │──────────┐
        │          └──────────┘          │
        │ 成功          │ 超时            │ 失败
        ▼               ▼               ▼
   ┌─────────┐   ┌──────────┐   ┌─────────┐
   │ SUCCESS │   │ TIMEOUT  │   │ FAILED  │
   └─────────┘   └──────────┘   └─────────┘
        │               │               │
        └───────────────┴───────────────┘
                        │
                  记录 AgentExecution
                  (日志 + 快照 + 耗时)
```

**执行日志标准字段**（AgentExecution）：

| 字段 | 类型 | 说明 |
|------|------|------|
| agentCode | String | 执行的 Agent 标识 |
| status | Enum | RUNNING / SUCCESS / FAILED / TIMEOUT / CANCELLED |
| referenceType | String | 关联的业务实体类型（如 ticket） |
| referenceId | Long | 关联的业务实体 ID |
| executedBy | Long | 执行者（用户 ID） |
| executedOn | String | 执行位置（server / client） |
| durationMs | Long | 执行耗时（毫秒） |
| tokenCount | Integer | Token 消耗（仅 HTTP_API 类型） |
| inputSnapshot | String | 输入快照（截断至 2000 字符） |
| outputSnapshot | String | 输出快照（截断至 2000 字符） |
| errorMessage | String | 错误信息 |

### 前端 Agent 运行时标准

前端 Agent 运行时采用 **Registry + Executor + Hook** 三层架构，参考 Anthropic 的可组合模式设计：

```
┌─────────────────────────────────────────────┐
│              AgentContext (Provider)          │
│  App 初始化时注册 Executor + 加载 Definition   │
└─────────────────┬───────────────────────────┘
                  │
┌─────────────────▼───────────────────────────┐
│           AgentRegistry (单例)               │
│  ┌─────────────────────────────────────┐     │
│  │ definitions: Map<code, Definition>  │     │
│  │ executors:   Map<type, Executor>    │     │
│  │ bindings:    Map<capability, code>  │     │
│  └─────────────────────────────────────┘     │
│  resolve(code) → { definition, executor }    │
│  resolveByCapability(cap) → { def, exec }    │
└─────────────────┬───────────────────────────┘
                  │
┌─────────────────▼───────────────────────────┐
│           useAgent / useAgentStream          │
│  execute(input) → AgentExecuteResult         │
│  executeStream(input) → AsyncGenerator       │
│  自动上报执行结果到后端                         │
└─────────────────────────────────────────────┘
```

**Executor 接口标准**：

```typescript
interface AgentExecutor {
  // Executor 支持的 Provider 类型
  providerType: ProviderType;

  // 当前环境是否可用（如 CliExecutor 仅在 Tauri 环境可用）
  isAvailable(): boolean;

  // 同步执行
  execute(definition: AgentDefinition, input: AgentExecuteInput): Promise<AgentExecuteResult>;

  // 流式执行（可选）
  executeStream?(definition: AgentDefinition, input: AgentExecuteInput): AsyncGenerator<AgentStreamChunk>;
}
```

**新增 Executor 规范**：
1. 实现 `AgentExecutor` 接口
2. 在 `AgentContext` 的初始化阶段注册到 `AgentRegistry`
3. `isAvailable()` 必须准确反映当前环境能力（如检测 Tauri 环境）
4. 异常必须捕获并返回 `{ success: false, error: ... }`，不得抛出未处理异常

### Agent 与 Workflow 集成标准

**设计保证：任何标准化定义的 Agent 都可以作为 BPMN 工作流节点使用，无需为每个 Agent 编写专属 Delegate。**

核心机制是 `AgentTaskDelegate` — 一个通用的 Flowable JavaDelegate，通过 BPMN 节点参数 `agentCode` 动态加载并执行任意已注册的 Agent。

#### 集成架构

```
BPMN 流程定义
  │
  ├─ ServiceTask (agentCode="gemini-translate")
  │     ↓
  │   AgentTaskDelegate.execute(execution)
  │     ↓ 读取 execution.getVariable("agentCode")
  │     ↓ 判断 executionEnv
  │     │
  │     ├─ SERVER_ONLY / BOTH → AgentDispatchService.executeOnServer()
  │     │     ↓ 同步执行，结果写入流程变量
  │     │     ↓ 流程自动继续下一节点
  │     │
  │     └─ CLIENT_ONLY → 创建 TaskInstance + ReceiveTask 等待
  │           ↓ SSE 通知客户端
  │           ↓ 客户端 claim → 本地执行 → REST complete
  │           ↓ WorkflowTaskBridge.signal() 唤醒流程
  │           ↓ 流程继续下一节点
  │
  ├─ ServiceTask (agentCode="notebooklm-reply")
  │     └─ 同上，CLIENT_ONLY 路径
  │
  └─ ServiceTask (agentCode="openai-audit")
        └─ 同上，SERVER_ONLY 路径
```

#### Agent 类型与工作流行为矩阵

| executionEnv | 工作流行为 | 流程节点类型 | 延迟特征 |
|-------------|-----------|------------|---------|
| `SERVER_ONLY` | **同步执行** — ServiceTask 内直接完成 | ServiceTask | 低（秒级） |
| `BOTH` | **优先同步** — 服务端优先执行 | ServiceTask | 低（秒级） |
| `CLIENT_ONLY` | **异步等待** — 创建任务 → 等待客户端完成 → 唤醒 | ServiceTask + ReceiveTask | 高（依赖客户端在线） |

#### 新增 Agent 时的工作流影响

| 操作 | 是否需要修改 BPMN | 说明 |
|------|----------------|------|
| 替换同 capability Agent | 不需要 | 通过 AgentBinding 动态切换 |
| 修改 Agent 配置参数 | 不需要 | 在 AgentDefinition.providerConfig 中更新 |
| 在现有流程中添加新 Agent 节点 | 需要 | 新增 ServiceTask 并配置 agentCode |
| 新建全新业务流程 | 需要 | 设计新的 BPMN 流程文件 |

#### BPMN 中配置 Agent 节点示例

```xml
<serviceTask id="translateTask" name="AI 翻译"
             flowable:delegateExpression="${agentTaskDelegate}">
  <extensionElements>
    <flowable:field name="agentCode" stringValue="gemini-translate"/>
    <flowable:field name="inputVariable" stringValue="ticketContent"/>
    <flowable:field name="outputVariable" stringValue="translationResult"/>
  </extensionElements>
</serviceTask>
```

只需更改 `agentCode` 的值，即可切换该节点使用的 Agent — 真正做到 Agent 即插即用。

#### 已知限制（v0.5 修复计划）

- WorkflowTaskBridge 事件监听器（CLIENT_ONLY Agent 完成后唤醒流程）的完整连接需要在 v0.5 中验证和加固
- 当前仅 ticket 业务注册了工作流回调，新业务模块接入时需注册对应的 WorkflowCallbackRegistry 回调

### Agent 编排模式

参考 Microsoft Azure 的 5 种编排模式和 Anthropic 的 5 种可组合模式，Simsonn AutoPilot 在 v0.4 阶段采用以下编排策略：

#### 当前实现的模式

| 模式 | 对应实现 | 说明 |
|------|---------|------|
| **顺序编排** (Sequential) | 工单状态流转 | PENDING_TRANS → TRANSLATING → PENDING_REPLY → ... 线性管道 |
| **路由分发** (Routing/Handoff) | AgentBindingService | 按 capability 路由到具体 Agent，支持动态切换 |
| **异步委托** (Async Delegation) | AgentTaskDelegate + WorkflowTaskBridge | BPMN 节点创建 TaskInstance → 客户端异步执行 → 唤醒流程 |

#### 未来规划的模式（v0.6+）

| 模式 | 计划用途 | 优先级 |
|------|---------|--------|
| **并行编排** (Concurrent) | 多 Agent 同时翻译，取最优结果 | 中 |
| **评估-优化** (Maker-Checker) | AI 翻译 + AI 审核的迭代循环 | 中 |
| **多 Agent 协作** (Group Chat) | 复杂工单需多个 Agent 协商回复策略 | 低 |

**复杂度控制原则**（参考 Azure 架构指南）：

| 级别 | 说明 | 何时使用 |
|------|------|---------|
| 直接模型调用 | 单次 LLM 调用 + 精心设计的 Prompt | 分类、摘要、简单翻译 |
| 单 Agent + 工具 | 一个 Agent 调用多种工具 | 单一领域的动态任务 |
| 多 Agent 编排 | 多个专业 Agent 协调 | 跨领域、需要安全隔离、或并行专业化 |

> **原则**：能用单 Agent 解决的问题不引入多 Agent。决策和流控的开销通常超过拆分为多个 Agent 的收益。

### Agent 可观测性标准

参考业界 AgentOps 和 OpenTelemetry GenAI 可观测性规范，建立 Agent 可观测性三大支柱：

#### 1. 执行日志 (Logging)
- 每次 Agent 执行自动记录到 `ai_agent_execution` 表
- 前端和后端执行统一上报格式（AgentExecutionReport）
- 输入/输出快照自动截断（防止大对象）
- 错误信息结构化记录

#### 2. 统计仪表盘 (Metrics)
- 按 Agent 维度聚合：总执行次数、成功率、平均耗时、Token 消耗
- API 端点：`GET /api/v1/agents/stats`
- 支持按时间范围过滤

#### 3. 健康状态 (Health)
- Agent 定义的启用/禁用状态
- Executor 可用性检测（`isAvailable()`）
- Provider 连通性测试（HttpApiAgentProvider.testProxy）

### 新增 Agent 标准流程

#### 场景一：新增 HTTP_API 类型 Agent（如接入 Claude API）

```
1. 后端：无需写代码
   → POST /api/v1/agents/definitions 创建定义
   → providerType: HTTP_API, executionEnv: SERVER_ONLY
   → providerConfig: { baseUrl, model, apiKey, maxTokens, systemPrompt }

2. 绑定能力（可选）：
   → PUT /api/v1/agents/bindings/{capability} 设置绑定

3. 测试：
   → POST /api/v1/agents/execute/{code} 服务端执行验证

4. 完成：前端 AgentRegistry 下次 reload 自动加载新定义
```

#### 场景二：新增自定义 Provider 类型（如 WebSocket Agent）

```
1. 后端：
   → ProviderType 枚举新增 WEBSOCKET
   → 实现 WebSocketAgentProvider implements AgentProvider
   → @Component 注册到 Spring 容器
   → AgentDispatchService 自动通过 providerMap 发现

2. 前端：
   → AgentProviderType 类型新增 'WEBSOCKET'
   → 实现 WebSocketExecutor implements AgentExecutor
   → AgentContext 初始化时注册: registry.registerExecutor(new WebSocketExecutor())

3. 创建 Agent 定义：
   → POST /api/v1/agents/definitions
   → providerType: WEBSOCKET

4. 测试 + 文档同步
```

### 与业界标准的对齐

| 业界标准/规范 | Simsonn AutoPilot 对应实现 | 对齐程度 |
|-------------|--------------------------|---------|
| **MCP (Model Context Protocol)** | AgentProvider SPI + providerConfig JSON | 概念对齐（工具接入标准化），未直接实现 MCP 协议 |
| **Agent Skills (Anthropic)** | AgentDefinition + capability 标签 | 概念对齐（能力声明 + 动态加载） |
| **AGENTS.md (OpenAI)** | CLAUDE.md Agent Teams 配置 | 概念对齐（项目级 Agent 指令） |
| **Azure Agent Orchestration** | Workflow + AgentTaskDelegate | 实现了顺序/路由/异步委托三种模式 |
| **OpenTelemetry GenAI** | AgentExecution 日志 + Stats API | 基础对齐（执行日志 + 指标聚合） |

#### v0.6+ MCP 对齐路线

当 MCP 生态进一步成熟时，计划将 AgentProvider SPI 升级为 MCP 兼容接口：

```
当前：AgentProvider.execute(input, config) → AgentExecuteResult
未来：MCP Client → MCP Server（Agent 作为 MCP Tool 暴露）
```

这将使 Simsonn AutoPilot 的 Agent 能力可以被外部 MCP 客户端（如 Claude Desktop、Cursor）直接调用。
